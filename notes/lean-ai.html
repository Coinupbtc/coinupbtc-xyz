Half of what it reads, it already read

An agent call doesn't send a question. It sends the whole session so far: the system prompt, every tool schema, every earlier message, and every tool result. When the agent runs cat on a 6,000-token file at step 3, those 6,000 tokens are read again at step 4, 5, 6 and every step after, until the session ends.

I rebuilt each session message by message and checked the rebuild against what Hermes itself recorded. It accounts for 87–88% of the measured tokens; the rest is chat-template tokens, reasoning and context injected per turn, which I report as "not rebuilt" rather than guess at. In that rebuild, old tool output is half of everything read. On my main profile from Oct 20 to 28, terminal and read_file results made up 73% of it, and each tool-output token was read 54 more times after it first arrived.

The countermeasure was already in Hermes

Hermes ships compression.proactive_prune_tokens. Past a trigger size it replaces tool results over 8,000 characters, outside the last few messages, with a one-line summary. The default is 0, off, and the comment beside it in Hermes' config says why it exists: the normal threshold "rarely fires on large windows, so old tool output is re-sent every turn". That is exactly the curve in the table above.

Before switching it on, I replayed nine days of sessions under its rules. The replay used the summary size Hermes really produces (a median of 44 characters over 400 real outputs) and the prompt-cache break each prune causes.

The recompute is small next to the 139 M tokens of cache misses that already happened in those nine days. Since Oct 28 at 23:20 the main profile runs with a 48,000 trigger. A replay counts tokens; it can't know whether the agent needed the text it lost. The live trial watches for that through two guards that should not move: repeat calls and failed tool calls.

What this doesn't say

Re-reading isn't expensive to compute here. The engine's prefix cache serves most of a request from memory, as my earlier note says. But carried tokens still fill the window, still cost attention on every token generated, and on a paid API are billed at the cache-read rate. Lean calls inventory waste even when the warehouse is free.

The rebuild doesn't model reasoning text, tool schemas are measured as of today, and cache misses are only judged in sessions whose engine reports cache hits (September's mostly didn't, so it has no miss rate). Lead time is wall time between stored messages, so a model step includes queueing. All of it is in the method.
